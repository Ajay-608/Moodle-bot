MOODLEBOT — RENDER DEPLOYMENT
=============================

Architecture:

GitHub
  -> Render Web Service
  -> Gunicorn
  -> Django
  -> fresh Render PostgreSQL

Render Build Command:
pip install -r requirements.txt && python manage.py migrate --noinput && python manage.py collectstatic --noinput && python manage.py initialize_production

Render Start Command:
gunicorn --bind 0.0.0.0:$PORT --timeout 180 moodlebot.wsgi:application

The Web Service uses Render's assigned PORT. Django serves collected static
files through WhiteNoise; Nginx is not part of this Render setup. Production
settings require SECRET_KEY and DATABASE_URL when DEBUG=False. Set DEBUG=False
and all secrets in the Render environment, not in Git.

`initialize_production` runs after migrations and collectstatic. It optionally
creates a configured deployment administrator, initializes the knowledge
corpus only when Documents are empty, then ensures a valid FAISS index exists.
The production database is fresh; SQLite users, chats, Documents, IDs, and
the old FAISS index are not migrated or reused.

FAISS is derived, rebuildable data. `build_index.py` and `rag_engine.py` use
the same `FAISS_INDEX_PATH` setting. The default is the project-local
`rag_index.faiss`; Render Free does not guarantee filesystem persistence.
If the index disappears or becomes stale, the first RAG request rebuilds it
from PostgreSQL under a cross-process lock. The generated file is ignored by
Git; no persistent disk, manual upload, or Render Shell is required.

Vectors use all-MiniLM-L6-v2 (384 dimensions) and the current PostgreSQL
Document IDs. The builder validates dimensions, vector count, ID set, and a
content fingerprint, and writes the index and metadata atomically. The engine
and embedding model are reused within each worker process; Gunicorn's default
single worker is retained for memory.

Local development can use SQLite and local-only populate_sample_data.
Production does not run sample-data seeding, fixture import, or destructive
legacy loaders. SQLite export/validation scripts are optional legacy audit
tools and are not part of production deployment.

There is no render.yaml: the current plan is manual Dashboard setup so no
database or service is created by applying a Blueprint. Render's default TCP
health check is used; the project has no dedicated health endpoint.

The Render Web Service watches `main` with Auto-Deploy; this repository does
not create or manage Render resources. Prior AWS EC2/RDS and Nginx instructions
are superseded and are not the current target.
